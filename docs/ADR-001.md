# ADR-001: Supabase PostgreSQL as Single Source of Truth with Transactional Outbox to Derived Firestore Read Model

- **Status:** Accepted
- **Date:** 2026-10-25
- **Deciders:** Senior Full-Stack & Healthcare-Data Engineering Team
- **Consulted:** Architecture Review, Security & Compliance Lead

---

## 1. Context and Problem Statement

Elite Hospital's Inpatient Approvals Platform ingests automated approval requests from Exchange Web Services (EWS/IMAP), parses Egyptian healthcare clinical free-text, matches procedures against corporate contracts, and notifies case managers and insurance coordinators.

Previously:
1. Approvals were written directly to local JSON files (`data/inpatient_approvals.json`) and synchronized directly to Google Cloud Firestore from multiple ad-hoc endpoints and watcher loops.
2. The application suffered from:
   - Split-brain states between local files, Firestore documents, and Supabase tables.
   - Lack of relational integrity, ACID transactions, and state machine enforcement.
   - Vulnerability to lost updates and duplicate processing of Exchange email threads.
   - High risk of PHI leakage when client listeners accessed Firestore collections directly.

We need a unified, resilient, enterprise data architecture where:
- Clinical data integrity, audit history, and state transitions are strictly ACID-guaranteed.
- Exchange email watermarks and message deduplication are transactional.
- Frontend real-time reactivity is maintained without exposing raw backend tables or unencrypted PHI.

---

## 2. Decision: The Transactional Outbox Pattern

We adopt **Supabase PostgreSQL as the authoritative single source of truth**, with **Google Cloud Firestore serving exclusively as an eventually consistent, derived read model** synchronized via a **Transactional Outbox Table + Asynchronous Replay Worker**.

```
+-------------------------------------------------------------------------+
|                       Supabase PostgreSQL (Source of Truth)             |
|                                                                         |
|  [EWS Ingestion] ---> BEGIN TRANSACTION                                 |
|                         1. Upsert public.inpatient_approvals            |
|                            (Unique message_id / hash, state machine)    |
|                         2. Insert public.outbox                         |
|                            (payload, status='pending')                  |
|                         3. Update public.sync_checkpoints (Watermark)   |
|                       COMMIT TRANSACTION                                |
+------------------------------------+------------------------------------+
                                     |
                                     | (CDC / Polling Loop)
                                     v
+-------------------------------------------------------------------------+
|                  Outbox Worker Service (Node.js / TS)                   |
|                                                                         |
|  1. Fetch pending outbox records (ORDER BY created_at)                  |
|  2. Transform & sanitize into client read model                         |
|  3. Idempotently write to Firestore (docId = approval_id)               |
|  4. On Success: Mark outbox status = 'published'                        |
|  5. On Failure: Exponential backoff; if retries >= 5 -> Dead Letter     |
+------------------------------------+------------------------------------+
                                     |
                                     v
+-------------------------------------------------------------------------+
|                       Firestore (Derived Read Model)                    |
|                                                                         |
|  - Real-time client subscription via onSnapshot()                       |
|  - Strict security rules (allowlisted @elitehospital.org domain only)   |
|  - 30-day automatic rollover retention window                           |
+-------------------------------------------------------------------------+
```

## 3. Core Architectural Guarantees

### A. Strict Inpatient Approval State Machine
Approvals in `public.inpatient_approvals` adhere to a formal state machine enforced by database `CHECK` constraints:
```
received ──> parsed ──> matched ──> needs_review ──> draft_created ──> answered
   │                                                         │
   └──────────────────────> refused <────────────────────────┘
```
- Transition timestamps are tracked in `state_timestamps JSONB` (e.g. `received_at`, `parsed_at`, `matched_at`, `drafted_at`, `answered_at`).
- Invalid states are rejected at the database engine level.

### B. Transactional Deduplication & Watermarking
- **Exchange Message-ID:** Stored with a `UNIQUE` constraint.
- **Content-Hash Fallback:** Computes `SHA256(sender || subject || date || body_fingerprint)` to catch duplicate deliveries where Exchange re-issues a new message ID.
- **EWS Watermarks:** Synchronization tokens (`sync_state_token`) are persisted to `public.sync_checkpoints` inside the same database transaction, eliminating watermark divergence.

### C. Resilience, Exponential Backoff & Dead-Letter Quarantine
- Outbox publishing uses exponential backoff:
  $$\text{delay} = \min(300, 2^{\text{retry\_count}} \times 2)\text{ seconds}$$
- When a message fails 5 consecutive times, it is quarantined to `public.dead_letter_queue` with the full error trace, preventing pipeline stalls (poison message quarantine).

### D. Complete Replayability
Because PostgreSQL retains the complete immutable transaction log and outbox history, the entire Firestore read model can be reconstructed from scratch at any time:
```bash
npx tsx scripts/outbox-worker.ts --replay-all
```

## 4. Consequences & Trade-offs

### Positive
- **Guaranteed Consistency:** No phantom approvals or partial writes. Every Firestore update reflects an approved Postgres transaction.
- **Zero Data Loss:** Outbox records survive worker crashes; pending rows are re-processed upon restart.
- **Auditable & Reversible:** Complete history of overrides and transitions preserved in PostgreSQL `audit_log`.

### Negative / Trade-offs
- **Eventual Consistency Latency:** Updates appear in Firestore with a typical delay of 200–800ms depending on outbox worker polling interval. (Acceptable for hospital approval workflows).
- **Dual Infrastructure Maintenance:** Requires running both PostgreSQL and the Outbox synchronization worker.
